1 — Why protocol stacks exist

Industrial devices speak different wire languages. A protocol translation service sits between them and moves meaning — not raw bytes — from one format to another.

Without layers

  • Partial Transmission Control Protocol reads break parsers
  • Serial noise desynchronizes streams
  • Reconnects tangle with application logic
  • You cannot tell which layer failed

With layers

  • Physical adapter owns sockets
  • Framer owns delimiters and checksums
  • Session owns timers and correlation
  • Domain model owns process meaning

5 — Sessions and correlation

  • Single in-flight request per channel keeps correlation simple (transaction identifier on Modbus Transmission Control Protocol; sequence on Distributed Network Protocol 3; “next frame” on Remote Terminal Unit).
  • Still read while waiting so unsolicited messages cannot deadlock the session.
  • Separate connectivity (connect / backoff) from protocol session (only runs while connected).
  • Nested enums for select-before-operate, file transfer, and startup integrity sequences.

6 — Case study: Modbus (rodbus)

RustTokio actorOne Application Data Unit, two coats

  • Shared protocol data unit; Transmission Control Protocol uses Modbus Application Protocol headers; serial uses unit identifier + cyclic redundancy check.
  • Remote Terminal Unit receive framing uses function-code length tables (not silence detection); transmit still applies 3.5 character-time gaps.
  • Channels start disabled; bad framing fails the session; Modbus exceptions do not.
  • Server maps many unit identifiers to handlers — gateway friendly.
PhysLayer → FrameWriter/FramedReader → ClientLoop/SessionTask → Channel/RequestHandler

7 — Case study: Distributed Network Protocol 3 (dnp3)

RustLink + Transport + ApplicationUnsolicited

Figure 8 — First/Final flags reassemble multi-frame application messages before object parsing.

  • Link: sync 0x05 0x64, cyclic redundancy check blocks, frame count bit.
  • Transport: first/final/sequence assembler (Empty → Running → Complete).
  • Application: zero-copy object header parse; codegen for variations.
  • Master prioritizes automatic tasks (restart, integrity, unsolicited enable) with one transaction at a time.
  • Outstation: event database, duplicate hash detection, select-before-operate.

8 — Case study: IEC 61850 (libIEC61850)

C99Dual planeModel as database

Figure 7 — Missing the publisher/subscriber plane means missing protection-speed events.

  • Client/server: Hardware Abstraction Layer → Transport Packet / Connection-Oriented Transport Protocol → ISO session/presentation → Association Control → Manufacturing Message Specification → Abstract Communication Service Interface.
  • Publisher/subscriber: Generic Object Oriented Substation Event and Sampled Values on Ethernet (hand Basic Encoding Rules).
  • Substation Configuration Language compiled offline to static C models (or dynamic APIs / text config).
  • Threading: multi, single, or threadless poll via stack_config.h.
  • Your folder’s Library_IEC61850-1.6 is the same lineage at 1.6.0; prefer libiec61850-1.6_develop (1.6.2) for study.

10 — Translation service blueprint

Figure 6 — Translation through meaning, not through byte tunnels. Green = measurements, amber = commands.

  1. Define canonical points: id, value, quality, time, origin.
  2. Data-driven mapping files (versioned).
  3. Bounded event queues with an explicit shed policy.
  4. Authorize after decode, before side effects.
  5. Honor select-before-operate when either peer requires it.
  6. Deliver incrementally: fake adapters → one southbound → one northbound → commands → chaos tests.

11 — Trade-offs and checklist

Printable checklist highlights
  • Hard maximum frame size before copy
  • Parser reset() on errors
  • Unique socket ownership
  • Unsolicited cannot complete the wrong promise
  • Mapping data-driven; quality preserved
  • Health shows session states; chaos-test reconnects
